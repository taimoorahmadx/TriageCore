# C15 · Explain CI diagnosis reliability and improve case browsing
Spec: FR-C6, FR-V4, I1, I2 · Owner: Shazil · Depends: C11, C14

**Goal:** Make the CI Engine catalogue navigable at corpus scale and make its diagnosis, reviewed label, and escalation reasons understandable. Enforce the owner-approved FYP-1 policy that a most-probable `bug` diagnosis escalates; do not introduce new loss costs or fit weights.

**Read first:** `docs/contracts/engine_io.md`, `docs/adr/004-bayesian-confidence-engine.md`, `docs/plan.md`, `src/core/models.py`, `src/core/engine.py`, `src/core/evidence.py`, `src/core/weights.yaml`, `src/agents/ci_pipeline.py`, `src/api/ci_routes.py`, `frontend/src/ci/CIEngineScreen.jsx`, `tests/test_engine.py`, `tests/test_ci_pipeline.py`, `tests/test_ci_routes.py`, `tests/fixtures/weights_synthetic.yaml`.

**Steps**
1. Implement the approved output amendment in `docs/contracts/engine_io.md` and `src/core/models.py`: add `diagnosis_reliable: bool` to `ConfidenceEngineOutput`. Set it false when no evidence is observed, the posterior is uniform, or evidence fit is below `unknown_pattern_floor`; otherwise true. Keep `classification` as the most-probable cause. Cover all reliability cases in engine tests.
2. Enforce the approved CI policy: if the most-probable CI diagnosis is `bug`, the engine policy must choose `escalate`; include a traceable reason. Keep `auto-fix` blocked unless exactly one commit is attributed and unambiguous. Update the evaluation's acceptable-action mapping so `bug` expects `escalate`. Do not change probabilities or loss costs.
3. In the CI Engine result, label diagnosis reliability clearly and show why escalation was selected, including fact-extraction/pipeline failures, blocked actions and reasons, and expected losses. Keep reviewed historical labels hidden until analysis. Replace the ambiguous “True label” wording with “Reviewed cause” or “Fixture expected cause”; render a clear “No reviewed label” state instead of silently substituting `unknown`.
4. Make the case catalogue usable for 200+ entries: compact rows in a bounded independently scrolling pane, search by repository/run/case ID, and filters for historical runs vs fixtures. Add a small curated quick-start group using stable case IDs, while keeping historical labels hidden before analysis.
5. Add or update tests for the reliability field, bug escalation, corrected action scoring, catalogue filtering/source privacy, and rendered escalation explanation as supported by the existing test setup.
6. Update `docs/adr/004-bayesian-confidence-engine.md` and `docs/plan.md` to record that the approved diagnosis-reliability and bug-escalation decisions are implemented. Add a row to `docs/log/changes.md` and refresh `docs/progress.md` after checks pass.

**Check:** `.venv/bin/python -m pytest -q tests/test_engine.py tests/test_ci_pipeline.py tests/test_ci_routes.py`; `make weights`; `make sensitivity`; `cd frontend && npm run lint`; `cd frontend && npm run build`.

**Done when:** reliable vs. unreliable diagnoses are explicit, CI bug diagnoses escalate, users can understand every escalation, and the CI case list is practical to browse without revealing labels before analysis.
**Stop and ask if:** an implementation step requires changing the owner-approved evidence contract, a new loss cost, CI probability values, or label semantics.
